# Working on ReviewBench (instructions for Claude sessions)

ReviewBench is an open benchmark that scores AI pull-request reviewers. The
owner (marshfalex) wants it built **steadily and autonomously**: sessions start
on a schedule, pick the next roadmap item, do it well, and open a PR. The owner
only reviews and merges. Read this file, `ROADMAP.md`, the last entries of
`docs/JOURNAL.md`, `docs/SPEC.md`, `docs/RISKS.md` and `docs/LESSONS.md` before doing anything.
Treat RISKS as standing priorities: never publish a claim it says isn't supported yet. Follow the
pre-PR checklist in LESSONS, and add a lesson (ideally with a test) whenever something goes wrong.

## Each session, in order
1. **Check open PRs first.** For each open PR you (Claude) authored: if CI is red, fix it; if review
   comments exist, address them. If **2 or more** of your PRs are still open and unmerged, do not
   start new roadmap work; fix what's open, write the journal entry, and stop. The owner is the
   bottleneck by design.
2. Otherwise take the **first unchecked item** in `ROADMAP.md` whose prerequisites are met. Skip
   items marked `[owner]` (they need the owner). If an item is too big for one session, split it
   in the roadmap and do the first part.
3. Work on a new branch `claude/<short-topic>`, keep the PR small and reviewable (one roadmap item,
   or ~5 cases at most), and make sure `ruff check .`, `python -m reviewbench validate` and
   `pytest` all pass before pushing.
4. Open a PR against `main`. Then **edit the PR description to remove any footer the tool
   appended** ("Generated by ...", session links). The owner wants descriptions clean.
5. Tick the roadmap item (or note partial progress) **in the same PR**, and append an entry to
   `docs/JOURNAL.md`: date, what you did, what you learned (surprises, dead ends, decisions and
   why), and what the next session should do. The journal is the project's memory; keep entries
   short and concrete.

## You may do without asking
- Implement roadmap items; refactor; improve tests and docs; fix CI.
- Write new **synthetic** cases (follow `docs/SPEC.md`; validate them; keep `repo/` minimal).
- Import public CVE cases **already approved** in `ROADMAP.md`, after pinning the exact fix
  commit and verifying a permissive license; record provenance in `case.yaml`.
- Trigger the `benchmark` workflow with **free providers only** (groq, gemini, openrouter `:free`
  models, cerebras, mistral), at most one run per provider+model per session; runs for different
  models may go in parallel.
  You usually don't need to: the workflow runs itself every 6 h, works through `lineup.yaml`
  (each model whose key secret is set) and resumes partial results until each is complete.
  To add a model to the comparison, add it to `lineup.yaml` in a PR.
- Add items to the bottom of `ROADMAP.md` under "Ideas (unapproved)" when you notice something
  worth doing; the owner promotes them.

## Never
- **Spend money.** No paid provider runs (anthropic or anything else), no paid services. If a task
  needs money, mark it `[owner]` in the roadmap and explain the estimated cost.
- Push to `main`, merge PRs, approve PRs, or rewrite history on shared branches.
- Post GitHub comments, reviews or issues under the owner's account.
- Commit held-out cases or anything that reveals them (see SPEC "Splits"). Held-out cases live in
  the owner's private repo and are loaded from `REVIEWBENCH_HELDOUT`.
- Change repository settings, secrets or workflows' permissions; add dependencies with
  non-permissive licenses.
- Inflate results: every reported number keeps its n and Wilson 95% CI, nothing is cherry-picked,
  and benchmark versions are never mixed in one comparison.

## Conventions
- Python 3.11+, ruff, pytest. Scoring and stats are unit-tested with no API calls.
- Commits end with `Co-Authored-By: Claude <noreply@anthropic.com>`; no session links.
- PR titles are plain and descriptive; descriptions say what changed and how it was verified.
